Case study · Aug 2026 – Nov 2026

CareKind AI

A documentation assistant for Australian aged care. A care worker describes what happened; the system drafts a structured note; nothing becomes a record until a qualified person confirms it.

01The problem

Aged-care staff often write their notes at the end of a long shift, from memory. Details get lost, required fields get missed, and changes across shifts go unnoticed. In a complaint or an investigation, those notes are the evidence.

An AI can take a spoken or typed account and turn it into a structured note in seconds. The risk is the other half: an AI that files records, makes clinical calls, or quietly turns a guess into a fact. So the product was built around one rule. The AI only ever drafts. A person in the right role confirms.

02From a spoken note to a confirmed record

The worker pipeline runs six stages and stops at "awaiting review". Rules come before drafting: a versioned rule registry decides what gets flagged, so the model may suggest but only rules may assert, and every flag carries its rule ID and version. The last stage traces each drafted sentence back to what the worker actually said and flags anything it cannot trace.

03Making the unsafe path impossible

"Only a confirmed draft becomes a record" is easy to promise and easy to break by accident. I designed the contracts so that breaking it does not compile into the system in the first place.

A reader and a writer

The record store is two ports. The writer has a single method, create a confirmed record, with no update and no delete. Interface tests check that only the confirm gate may hold it, and the database role can only select and insert.

No "confirmed" job state

The worker's job status stops at "awaiting review". There is no confirmed state to reach, so no pipeline bug can promote a draft on its own.

Ports for every vendor

Transcription, retrieval, drafting, rules, storage, media and the care-system link are all ports in a shared contracts package. The backend never calls a vendor SDK directly, so any one of them can be swapped without touching a route.

Contracts down to status codes

I specified the six core endpoints with every failure case. Confirming as the wrong role returns 403, a draft that fails grounding returns 409 unless the reviewer gives a reason, and a warning never turns into a block.

04Measuring it

I wrote a 30-case golden set of synthetic care notes, ten held out, with inference traps such as a worker saying "maybe a UTI", which must never become a diagnosis. These are development numbers, not release evidence: the cases are still marked as candidates, not agreed by a clinician.

  • The latency budget was set before anything was measured, and marked as un-benchmarked until it was. On 20 live typed notes the pipeline took 6.4 s at the median and 8.2 s at p95, at about 1.4 US cents per draft. Voice was not measured.
  • The serious-incident screen caught all 56 incident cases with no false alarms on 106 others, but it was tuned on the development rows, so I do not count that as proof.
  • CI runs the backend and frontend tests and the offline evaluation on every pull request.

05What it is and is not

CareKind is a working product built and demonstrated by a ten-person team, using synthetic residents and notes only. It has not been clinically validated, it has no aged-care provider as a client yet, and the demo did not run in an Australian data region. The page says so because a safety product that overstates itself has already failed at its main job.
