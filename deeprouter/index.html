DeepRouter Skills Marketplace

01The problem

A skill is mostly a well-written prompt and some instructions. Sell it as a download that runs inside a coding agent such as Claude Code, and the prompt is no longer secret: anyone who buys it can read it. So what is the customer paying for, and how do you stop one purchase from becoming a thousand?

I led the second revision of the product design, which answered it this way. A skill ships as a package the user runs locally, but its work step calls DeepRouter's routing API with the user's own key. Every run is then authenticated, checked against the user's plan, and billed, and the server applies its own copy of the instruction template and its own model allowlist.

02Publishing a skill, and running one

The package a user downloads holds a SKILL.md that a coding agent recognises as a skill, a manifest with the skill and version IDs, the instruction template, a README, and a small runner that makes the call to the routing API.

03Decisions and trade-offs

Build the package when a version goes live

The zip is built inside the activation transaction and stored with its checksum, so what users download is exactly the version the API executes. My first attempt was reverted and re-landed in this form.

Check the plan on every run

A download is not a permanent right. Each call re-checks that the skill is enabled, the pinned version is live, and the user's subscription or one-time purchase still covers it, before the prompt loads or anything is billed.

Abuse limits on a public API

Per-key request limits, plus limits on how many IP addresses and clients one key may use in ten minutes, held in Redis. Revoked keys are re-checked against the database, not trusted from a cache.

Money paths that cannot double-charge

One-time purchases use an idempotency key and a conditional balance update. Referral rewards were moved after the purchase commits, once a failing referral was found to roll back a valid purchase.

05What happened next

After the first version shipped, the marketplace was rebuilt as version 2 by other engineers, and the runner was dropped. Their reasoning exposed the weak point in our design: a coding agent only reads the skill's text, so a user can copy the instructions and run them anywhere, and per-run checks only bind the runs that go through the API. The design had said as much up front, that it holds only if calling the API is genuinely useful. If I did it again I would test that assumption with real users before building the enforcement around it.
